# 聊天业务执行框架计划

状态：方案草案，尚未实施。日期：2026 年 11 月 5 日。

## 目标与既有要求

老师可以通过连续聊天完成耗材管理业务。系统理解目标，查询正式数据，询问缺少的信息，计算需求，生成操作预览，并在明确确认后执行。老师可以在同一段对话中更正、取消、继续或查询结果。

harness 在本方案中指聊天业务执行框架，负责管理任务状态、可调用功能、输入校验、执行顺序、用户确认、结果验证和故障恢复。模型负责理解与组织任务，数量计算和数据变更由现有业务代码完成。

继续使用 FastAPI、SQLite 和现有网页技术；校园网及学校 VPN 访问，无需登录，操作人姓名未经身份核验。AI 使用机构允许的接口。正式库存、操作历史和对话任务状态保存于校内。现阶段按用户要求使用 HTTP；可信 HTTPS、学校 VPN 实际访问和手机后台通知分别保留待验证状态。

## 当前实现与需要增加的能力

- `genai.py` 调用实际模型，已有有限重试、可配置备用模型和健康检查。
- `services.py` 将自然语言转为入库、消耗、借还和预警等库存操作预览。
- `ledger.py` 统一处理 Decimal 数量、事务、版本、请求去重及关联撤销。
- `workflows.py` 已有借还相关资料、采购、实验预留、清点、转移和导入等业务规则。
- `server.py` 已有统一写入入口和原请求结果查询。
- 网页草稿和不确定请求主要保存在浏览器中。目前缺少服务端对话任务、跨步骤执行记录、完整业务功能定义和连续追问机制。

新增框架调用这些既有功能。聊天与表单必须遵循相同规则、产生相同历史记录，并通过同一组库存测试。

## 教师操作方式

聊天成为默认页面，支持自然语言、附件和就近操作卡片。老师可以用文字继续补充资料，卡片辅助展示具体物品、实验时间、计算过程及执行结果。

示例过程：

1. 老师说：“明天下午给 36 名学生准备酸碱滴定，每组 2 人。”
2. 系统查询已有实验模板。没有明确模板时要求选择或说明物品；已有模板时计算 18 组需求，并询问准确时间、场地和负责人等必要信息。
3. 系统查询可分配库存，展示各位置、实际差值、已订购数量和预计到货。借用与消耗分别列明。
4. 老师说：“改成 40 人，再多准备 2 个烧杯。”系统使旧预览失效，按 20 组重新计算并检查冲突。
5. 系统展示预留及采购草案。老师确认后，只执行所确认的内容，并返回实际生成的安排和采购记录。
6. 老师以后说：“这次归还 18 个，另外 2 个破损。”系统关联准确借用记录，确认归还物品状态后处理，不重复扣减柜内数量。

“先不要”“刚才数量写错了”“只处理其中一项”“确认执行”“查看刚才是否成功”均属于需要明确支持的对话动作。系统不能仅凭模型生成了一段完成说明就显示成功。

## 功能范围

| 业务 | 聊天中的完整行为 |
| --- | --- |
| 库存查询 | 名称检索，区分规格、单位与位置，查询各状态和指定时段可分配数量 |
| 入库与消耗 | 匹配具体物品，检查包装换算，生成并确认库存操作 |
| 借用与归还 | 登记人员、用途、位置和时间；关联未完成借用，处理部分归还、清洗、维修、破损和遗失 |
| 实验模板与安排 | 建立或修改模板，按人数和组数计算，检查整份安排，预留、执行或取消 |
| 采购 | 登记负责人、数量、预计到货，查询建议，处理部分到货和取消 |
| 清点与状态 | 记录实物数量及差异原因，完成清洗、维修及待核对状态变化 |
| 物品与位置 | 新增物品、维护资料、确认包装换算、部分转移、整个位置转移或停用，记录说明与照片 |
| 文件 | 在聊天中上传库存表或实验准备表，预览错误、重复和变更，再确认执行 |
| 预警与通知 | 设置阈值，查询未设置项，确认、暂缓及再次提醒，显示浏览器通知状态 |
| 历史与导出 | 按物品、课程、人员、日期和类型查询并导出，关联实际操作结果 |
| 撤销与恢复 | 检查可撤销范围和后续依赖，展示反向操作预览；查询并继续不确定请求 |

文件选择和浏览器通知授权通过聊天中的附件控件、授权按钮完成。后台推送继续只发送通用提醒。

## 执行框架设计

### 1．明确的业务功能定义

建立工具注册表。这里的“工具”指服务器允许 AI 请求的固定业务函数，例如查询库存、查询借用、计算实验需求、建立采购草案及确认执行。

每个工具声明用途、输入和输出字段、必填资料、是否写入、版本要求、预览方式、确认要求、完成验证和可撤销范围。输入输出使用 Pydantic 校验。模型不具备 SQL、shell、任意 URL 请求或绕过业务校验的执行能力。

模型只提出工具请求。服务器检查允许的功能和参数，并返回结构化结果。物品编号、借用编号、采购编号及安排编号必须来自查询结果或经过校验的用户选择，不能采用模型编造的编号。

查询工具直接执行。所有业务写入先形成预览，获得对应版本的确认后执行。模型及工具循环有明确次数、时间和输出大小限制，超过限制时保存任务并解释当前状态。

### 2．持续对话与任务状态

新增版本化数据库迁移，保存会话、消息、任务、任务步骤、功能调用结果和确认记录。服务端任务是恢复依据，浏览器保留输入草稿和当前会话标识。

任务状态至少包括：草案、待补充、待确认、执行中、已完成、部分完成、失败、已取消和已过期。每个步骤保存具体对象、数量、单位、时间、依赖关系及结果编号。

上下文由业务对象及已确认事实组成。较长对话可以压缩文字，但具体物品编号、数量、版本、待确认内容和未完成步骤必须完整保留。用户更换任务时明确建立新任务，不把上一个任务的数量或人员静默用于新任务。

默认只恢复本浏览器持有会话标识的对话。无需登录的要求不变，系统不将自填姓名描述为已验证身份，也不承诺同名人员之间的权限隔离。

### 3．只依据真实数据组织操作

库存、未归还数量、采购数量、实验需求和可分配数量全部来自业务查询与 Decimal 计算。模型组织说明，服务器校验引用的记录和计算值。

遇到多个容量、品牌、包装或位置时展示候选，并接受“301 那一项”之类的后续选择。系统重新解析到具体记录后才能继续。未说明的单位换算、归还状态及用途不能自动补全。

日期按上海时间理解，预览显示绝对日期、时间及所在时区。“明天下午”仍需要准确实验时段才能形成预留。历史发生时间与系统记录时间分别保留，模型不能改写审计时间。

### 4．预览与确认绑定

服务器生成具有版本和有效期的计划，确认绑定计划编号、内容摘要值、所引用数据版本、操作人及设备。聊天中的“确认”只对应当前仍有效的具体预览。

预览展示将变更的记录、各库存状态变化、安排和采购变化，以及不能自动完成的部分。仅确认预留时不能同时建立采购；取消任务后到达的旧确认请求必须拒绝。

用户修改人数、数量、位置、时间或操作范围后，旧确认立即失效。其他老师修改相关数据后，执行前重新校验；存在冲突时重新展示差异并要求确认，不能静默替换已批准内容。

### 5．多步骤事务与故障恢复

同一次确认、能够在同一数据库事务内完成的业务写入采用整体事务，全部成功或全部取消。调用模型期间不占用数据库写事务。

需要跨日期完成的采购到货、借还和实验执行，分别形成持久业务记录及后续步骤。对话显示每一步实际状态。已经发生的有效业务操作不会因为后一步失败而被描述为全部取消。

每个执行步骤使用固定请求编号，并关联任务编号、步骤编号和现有操作记录。断网或响应丢失时先查询原请求结果，不能自动生成新编号重做。未知结果保持待核对，恢复后核对已完成步骤再继续。

撤销调用现有反向操作和依赖检查。必须重新确认的后续写入不会由恢复进程自行执行。服务器重新启动后，也不能把“待确认”当成“已确认”。

### 6．模型可用性与运行记录

复用已有实际模型调用、有限重试、机构允许的备用模型及健康检查。模型服务暂时失败时保存对话任务和输入，明确显示失败；恢复后可以继续同一任务。不能保证模型提供方永不发生故障。

每次任务记录模型版本、所用工具、参数校验结果、耗时、错误类型和业务结果编号。日志不保存 API 密钥、完整推送订阅等凭据。

网页、附件单元格和物品备注均作为业务资料处理，其中出现的命令不能改变工具权限或跳过确认。模型输出中的 HTML 不直接执行。完整对话只按业务需要发送给机构允许的模型，普通浏览器推送不包含这些资料。

## 实施顺序

### 第一阶段：业务定义与只读对话

- 整理所有业务工具及读写、版本、确认和恢复要求，建立覆盖表。
- 实现会话、任务及步骤迁移，建立读取接口和只读工具执行器。
- 完成库存、借用、采购、安排、预警及历史的连续查询和追问。
- 聊天作为默认入口，实际数据在对话中展示，已有页面继续作为辅助操作方式。
- 验证标准：能连续解释真实查询结果、更正条件并区分物品；只读对话不会改变库存或采购、安排状态。

### 第二阶段：单项业务的聊天执行

- 完成计划、预览、确认和状态校验。
- 接入入库、消耗、借还、清点、状态变化、采购与到货、资料维护、转移及预警。
- 接入原请求结果查询、明确取消及依赖检查后的撤销。
- 验证标准：每种业务都能用连续聊天完成，确认过期、数据变化、重复发送和断网均不会造成错误或重复变更。

### 第三阶段：完整实验与文件流程

- 接入实验模板、人数计算、整份清单分配、预留、执行和取消。
- 接入库存及准备表附件的预览、人工匹配、重复检测和确认。
- 接入位置照片、位置管理、导出及通知设置。
- 验证标准：从准备实验、采购部分到货、执行、借还到清洗，可以始终保留在同一对话中，业务状态与现有页面一致。

### 第四阶段：真实模型验证与发布

- 建立脱敏教师对话样例和期望行为，覆盖常见表述、否定、更正、歧义、跨任务及恢复。
- 在正式数据库副本上验证迁移、恢复和并发，保留原始数据差异报告。
- 使用实际机构模型验证连续对话；用 Playwright 验证电脑、手机、附件和不确定请求。
- 在 GitHub 自动检查中加入工具契约、任务状态、确认及恢复测试。
- 同步通过验证的代码到 GitHub，记录提交编号；通过既有备份及恢复部署流程发布，并检查校园网 HTTP 和实际 AI。
- 可信 HTTPS、VPN 和真实手机后台通知按各自的外部条件继续验证。

## 必须通过的教师情境

1. 查询两种容量的烧杯，选择具体位置后借出 20 个，归还 18 个待清洗，另外 2 个破损，清洗完成后数量正确。
2. “不放回”“没有使用”“准备采购”“如果明天使用”均不会形成相反的库存变化。
3. 两项同时实验争用库存；先后实验需要归还并清洗；人数修改导致整份预览重新计算。
4. 登记订购 20 个，先到货 5 个，再查询剩余采购及当前可用数量；取消剩余采购不影响已到货部分。
5. 清点、规格校验、包装换算、部分转移、历史保留及依赖撤销遵守现有业务规则。
6. 用户在预览后更正、取消、更换任务或切换候选；旧确认不会执行。
7. 两位老师同时确认同一批库存；过期版本被拒绝，失败批量不改变任何库存。
8. 确认后网络中断、服务器重新启动、模型超时或重复消息；查询同一请求能够得到唯一结果并继续任务。
9. 附件含“忽略之前指令”等文字、模型输出非法工具或伪造编号；不会执行越权行为或跳过校验。
10. 页面声称完成的每项业务，均能查询对应数据库记录；只读问题、未确认草案和失败任务不产生库存变更。

业务功能覆盖表、数据库完整性、写入确认及恢复检查必须全部通过。真实模型评估同时记录正确完成、正确追问、明确拒绝和失败，不把需要追问的歧义问题算作已完成操作。

## 本次计划的实施边界

先完成固定业务工具、持久任务和确认机制，再扩展复合任务。具体工具数量和数据库结构在第一阶段依据现有接口逐项确定。本方案尚未修改已部署的库存业务行为，也不代表 HTTP 重新发布或外部验收已经完成。
